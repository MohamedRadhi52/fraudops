FraudOps

Sur huit semaines de test, le modèle ramène le coût de la fraude carte de $cost_none_short à $cost_lightgbm_short.

Une détection de fraude évaluée comme en production : modèle ré-entraîné chaque semaine, fraudes connues sept jours après la transaction, et une équipe qui ne peut contrôler que 100 cartes par jour.

LightGBM stoppe presque toutes les fraudes repérables

La Card Precision@100 est la part de vraies fraudes parmi les 100 cartes contrôlées chaque jour. Une carte dont une fraude est déjà connue est bloquée : le modèle est jugé seulement sur les fraudes que la banque ne connaît pas encore, d'où un plafond de $ceiling.

Ce qui manque vient d'un terminal compromis dont aucune fraude n'est encore connue : LightGBM ne stoppe que $stopped_unknown de ces fraudes, contre $stopped_known quand le terminal a déjà une fraude connue, $stopped_s3 pour les clients compromis et $stopped_s1 au-delà de 220 €. Tant que les premières étiquettes n'arrivent pas, rien dans les données ne trahit ces fraudes.

Le bon seuil n'utilise qu'un tiers de la capacité

Le seuil qui minimise le coût est choisi sur les semaines de validation, puis gardé sur le test. Pour LightGBM, il contrôle $controls_lightgbm cartes par jour et coûte $cost_lightgbm, contre $cost_full en utilisant chaque jour les 100 contrôles : au-dessous du seuil, une carte a trop peu de chances d'être frauduleuse pour justifier un contrôle à 10 €. La capacité restante absorbe les pics et peut servir à des contrôles aléatoires, seul moyen de mesurer la fraude que le modèle ne voit pas.

Des probabilités fiables, tant qu'on ne pondère pas les classes

Des probabilités calibrées permettent une règle sans réglage : contrôler une carte dès que probabilité × montant dépasse le coût d'un contrôle. Les semaines de test comptent $fraud_rate de fraudes.

$calibration_rows

Entraîné sans pondération, LightGBM est déjà calibré. Pondérer les classes, une pratique courante, gonfle les probabilités et fait contrôler 100 cartes par jour ; une calibration isotonique ajustée sur la validation les ramène au bon niveau.

Ce que le modèle regarde

Sur toutes les transactions, LightGBM regarde surtout l'habitude de dépense du client. Sur les $alerts transactions qu'il signale ($alert_fraud_share de fraudes), le montant et le taux de fraude du terminal sur 7 jours dominent. Exemple : $example_amount pour un client qui dépense $example_habit en moyenne sur 30 jours, perte attendue $example_loss ; ses trois raisons, renvoyées par l'API avec chaque score : $example_reasons.

SHAP explique le modèle, pas la fraude : des variables corrélées se partagent le crédit, et une variable absente de l'explication peut être remplacée par une autre qui porte la même information.

Ouverture de compte : l'âge pèse sur les faux positifs

Le jeu Bank Account Fraud (Feedzai, NeurIPS 2022) compte $baf_applications demandes sur 8 mois. Sa licence interdit l'usage commercial : un workflow GitHub Actions le télécharge, entraîne sur les mois 0 à 4, fixe le seuil à 5 % de faux positifs sur le mois 5 et teste sur les mois 6 et 7. Seuls les résultats sont publiés.

Équité entre groupes d'âge

Refuser à tort une demande légitime pénalise un client. Le papier compare donc les taux de faux positifs des 50 ans et plus et des autres : le ratio vaut 1 quand les deux groupes sont signalés à tort aussi souvent.

$fairness_rows
Variante50 ans et plusMoins de 50 ansRatioRappel

Un seuil par groupe égalise les faux positifs pour $mitigation_loss de rappel. Retirer l'âge ne suffit pas : d'autres variables portent la même information. Ce compromis se chiffre, mais il se décide avec le métier, la conformité et le juridique ; et aucune correction ne peut égaliser à la fois faux positifs, faux négatifs et calibration quand les taux de fraude diffèrent selon l'âge.

La dérive se voit sur BAF, pas sur le simulateur

Le PSI compare la distribution d'une variable à une période de référence. Au-delà de 0,1, on surveille le taux d'alertes et la calibration ; au-delà de 0,25, on ré-entraîne et on recalcule le seuil. Sur le jeu carte, le PSI ne dépasse pas $max_weekly_psi d'une semaine à l'autre : le simulateur est stationnaire. Sur BAF, conçu avec une dérive temporelle, certaines variables franchissent les seuils d'alerte.

Méthode

  1. 1,8 M de transactions simulées d'après le Fraud Detection Handbook (ULB, 2022), avec ses trois scénarios de fraude.
  2. Des features par fenêtres glissantes sur le client et le terminal ; celles du terminal ignorent les 7 derniers jours, dont les étiquettes ne sont pas encore connues. Deux tests le garantissent.
  3. Chaque semaine, un modèle entraîné sur les 28 jours précédents dont les étiquettes sont connues score la semaine suivante.
  4. Quatre semaines de validation pour tous les réglages, huit semaines de test pour les résultats, avec des intervalles de confiance par bootstrap sur les jours.

Limites

  • Les données carte sont simulées : les fraudes suivent des règles connues et les scores obtenus ne se transposent pas tels quels à des données réelles.
  • Les coûts sont des hypothèses : 10 € par contrôle, le montant pour une fraude manquée.
  • Pas de boucle de rétroaction : une transaction bloquée en production ne révèle jamais sa vraie étiquette.
